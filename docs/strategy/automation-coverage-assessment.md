# Atlassian Cloud: Automation Coverage Assessment

Documentation assessment | 21 October 2026

Baseline: requirements register v0.2; provisional profile `FS-COLLAB-01 v0.1`

**Build around supported product APIs, but do not assume every organisation guardrail can be reconciled as code.** Jira and Confluence have documented asset-configuration interfaces; the current Control API documentation marks key shared-policy operations deprecated and temporarily disabled ([Jira projects](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-projects/), [Confluence spaces](https://developer.atlassian.com/cloud/confluence/rest/v2/api-group-space/), [Control policies](https://developer.atlassian.com/cloud/admin/control/rest/api-group-policies/)).

The design should therefore combine API-backed configuration, executable firm policy, native SaaS enforcement and protected external evidence. This is a design recommendation, not a selected runtime or an assertion of implemented controls.

## Scope and assessment rules

- **Authoritative baseline:** All 52 requirements and 22 provisional parameter groups are retained from the [control requirements register](control-requirements-register.md).
- **Documentation, not tenant proof:** No tenant APIs were called, no settings were changed, no subscriptions were purchased and no timing targets were tested. Every implementation route below remains untested.
- **Entitlements are prerequisites:** Verify the actual organisation, product plan, Guard tier, rollout state and backup entitlement before accepting a documented feature as available. Audit-event visibility, export restrictions and backup purchase conditions differ by subscription ([audit coverage](https://support.atlassian.com/security-and-access-policies/docs/accessing-audit-log-activities/), [export controls](https://support.atlassian.com/security-and-access-policies/docs/prevent-data-export/), [backup eligibility](https://support.atlassian.com/organization-administration/docs/overview-of-atlassian-backups/)).
- **Read is not write:** An event stream, classification label or policy-impact flag is not evidence that the corresponding security setting can be configured through an API. Confluence's data-policy API, for example, exposes read-only blocking metadata rather than the complete shared-policy configuration ([data-policy API](https://developer.atlassian.com/cloud/confluence/rest/v2/api-group-data-policies/)).
- **Unknown stays explicit:** `n.a.` means the required public interface or guarantee was not verified in the reviewed documentation, not that no interface could exist. Private browser endpoints and undocumented GraphQL mutations are not accepted substitutes.
- **No completion percentage:** Compound requirements contain configuration, authority, behavioural and evidence clauses. An available endpoint does not establish that the whole control is automated or effective.

| Route | Meaning in this assessment |
| :--- | :--- |
| **API-backed** | Relevant public read/write operations are documented. Firm-side policy, orchestration and acceptance tests are still required. |
| **Firm automation** | The requirement is principally delivered by the firm's policy evaluation, CI/CD, identity, monitoring or evidence services, consuming SaaS interfaces where useful. |
| **Partial** | Some useful capability exists, but the required boundary, mutation, scope, timing or complete readback remains limited or unverified. |
| **Supplier assurance** | Vendor-operated behaviour requires scoped supplier evidence and compatibility assessment, not customer configuration alone. |
| **Restricted** | Immediate implementation keeps an excluded capability disabled; it does not build the later service. |

These are implementation-route labels, not new control domains or acceptance verdicts.

## Findings that affect the design

### Configuration and operating APIs

| Surface | Documented automation | Boundary and design treatment |
| :--- | :--- | :--- |
| **Jira projects and permissions** | Create a project using `POST /rest/api/3/project`; create/read/update permission schemes and assign them to projects through the permission APIs ([projects](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-projects/), [schemes](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-permission-schemes/), [assignment](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-project-permission-schemes/)). | Start with a bounded company-managed pattern and explicit scheme IDs. Do not infer complete workflow, field, notification and issue-security coverage from project creation alone; validate each owned property separately. |
| **Confluence spaces and access** | `POST /wiki/api/v2/spaces` supports private-space creation and access-related fields; legacy space-permission mutations and newer space-role assignment APIs are documented ([spaces](https://developer.atlassian.com/cloud/confluence/rest/v2/api-group-space/), [legacy permissions](https://developer.atlassian.com/cloud/confluence/rest/v1/api-group-space-permissions/), [space roles](https://developer.atlassian.com/cloud/confluence/rest/v2/api-group-space-roles/)). | Detect the tenant's permissions model before selecting an adapter. The v2 space-permissions page is read-only; do not mistake that for absence of all supported write APIs ([permission readback](https://developer.atlassian.com/cloud/confluence/rest/v2/api-group-space-permissions/)). |
| **Classification** | Organisation classification levels have management/publish APIs; Jira project defaults and Confluence space/page/blogpost classifications have read/write operations ([classification management](https://developer.atlassian.com/cloud/admin/dlp/rest/api-group-classification-level/), [Jira defaults](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-project-classification-levels/), [Confluence classification](https://developer.atlassian.com/cloud/confluence/rest/v2/api-group-classification-level/)). | Automate label/default application, but separately enforce permissions, app use and flow treatment. Jira's project-classification operations are marked experimental; version and regression-test that adapter ([Jira defaults](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-project-classification-levels/)). |
| **Automation rules** | Rule search/read/create/update/state/scope operations are documented; rule management became GA in August 2025 and disabled-rule deletion was added in March 2026 ([rule API](https://developer.atlassian.com/cloud/automation/rest/api-group-rule-management/), [changelog](https://developer.atlassian.com/cloud/automation/api/changelog/)). | Version rule definitions and connection references. Explicitly create template-derived rules disabled: omission of `state` creates them enabled; use `redactSensitiveFields` when retrieving supported rule details ([changelog](https://developer.atlassian.com/cloud/automation/api/changelog/)). |
| **Organisation policies** | Current Control documentation lists v1 and v2 policy operations, but marks list/get/create/update operations deprecated and temporarily disabled; validation/publish are also listed ([policy API](https://developer.atlassian.com/cloud/admin/control/rest/api-group-policies/)). | **Blocked as a dependable full reconciliation surface pending vendor confirmation.** A listed route or surviving publish operation does not prove working policy CRUD. Authentication-policy APIs separately expose membership assignment/readback, not the complete MFA/SAML/session-settings lifecycle ([authentication-policy API](https://developer.atlassian.com/cloud/admin/control/rest/api-group-authentication-policies/)). |
| **Identity and roles** | SCIM manages provisioned identities/groups; organisation APIs expose user/group and role/access operations ([provisioning API](https://developer.atlassian.com/cloud/admin/user-provisioning/rest/intro/), [users](https://developer.atlassian.com/cloud/admin/organization/rest/api-group-users/), [groups](https://developer.atlassian.com/cloud/admin/organization/rest/api-group-groups/)). | Use current v2 search/access routes, not removed v1 examples. Listed v1 endpoints stopped working in June 2026; some v2 GET listings have a later announced retirement, so new work should use the replacements ([admin changelog](https://developer.atlassian.com/cloud/admin/changelog/)). |
| **Approvals and asset metadata** | JSM exposes request approval read/answer operations; Jira entity properties support storing integration metadata ([request API](https://developer.atlassian.com/cloud/jira/service-desk/rest/api-group-request/), [entity properties](https://developer.atlassian.com/cloud/jira/platform/jira-entity-properties/)). | Consume current ServiceNow/JSM authority through a validated contract. Do not turn editable SaaS properties into the authoritative approval store; Jira warns against storing sensitive data in entity properties ([entity-property security](https://developer.atlassian.com/cloud/jira/platform/jira-entity-properties/)). |
| **Audit collection** | Organisation Events APIs expose cursor-based events, `events-stream` and webhook management; the documentation states different rate limits for search and stream operations ([Events API](https://developer.atlassian.com/cloud/admin/organization/rest/api-group-events/)). | Build resumable collection, deduplication, gap detection and protected retention. Do not copy the `/events` rate limit onto `/events-stream`; validate each route and the actual entitlement. |
| **Detection and redaction** | Guard Detect exposes alert queries/status updates and documented GraphQL bulk-redaction/restore operations; Jira/Confluence automation can respond to Guard detections ([alert/restore examples](https://developer.atlassian.com/cloud/guard-detect/developer/api-examples/), [bulk redaction](https://developer.atlassian.com/cloud/guard-detect/developer/bulk-redaction/), [Guard automation](https://support.atlassian.com/security-and-access-policies/docs/how-does-automation-work-with-guard-detect/)). | Treat these as bounded response actions, not universal inline DLP. Bulk redaction uses experimental opt-ins and asynchronous jobs; acceptance must verify the resulting content, not just job submission ([bulk redaction](https://developer.atlassian.com/cloud/guard-detect/developer/bulk-redaction/)). |
| **Backup and restore** | Public v2 APIs cover backup-policy management, backup/status retrieval, restore initiation, revalidation and progress ([Backup Management API](https://developer.atlassian.com/cloud/backup-management-apis/rest/api-group-public/)). | Do not dismiss recovery as UI-only. Still verify purchase eligibility, protected scope, clean-target prerequisites, timing and post-restore configuration before accepting P-19 ([backup overview](https://support.atlassian.com/organization-administration/docs/overview-of-atlassian-backups/), [restore requirements](https://support.atlassian.com/organization-administration/docs/restore-product-data-from-a-backup/)). |

### Boundaries that APIs do not remove

- **One-hour elevation has no verified native expiry contract:** Reviewed role APIs describe grants/revocations but do not establish a native one-hour human-grant TTL. Record native expiry as `n.a.` until verified; an IdP/PAM or scheduled revoker is the candidate route and must prove effective removal, including residual access ([user-role operations](https://developer.atlassian.com/cloud/admin/organization/rest/api-group-users/), [group-role operations](https://developer.atlassian.com/cloud/admin/organization/rest/api-group-groups/)).
- **SCIM deactivation is not universal revocation:** For external users, Atlassian says deactivation removes SCIM-group membership but site access can remain. SCIM-owned membership must be changed at the IdP, not through competing organisation group writes ([provisioning behaviour](https://support.atlassian.com/provisioning-users/docs/understand-user-provisioning/), [group-removal restriction](https://developer.atlassian.com/cloud/admin/organization/remove-user-to-group/)).
- **Privilege paths differ:** Atlassian explicitly warns that the group-removal operation does not modify the `site-admin` group and therefore does not revoke the org-admin role. Ordinary group removal cannot be accepted as proof of organisation-admin withdrawal ([group-removal restriction](https://developer.atlassian.com/cloud/admin/organization/remove-user-to-group/)).
- **Tokens and sessions are separate:** Managed-user token deletion and service-account token revocation are documented, but account-disable documentation does not state a guarantee for terminating existing sessions or tokens. The organisation-wide managed-token deletion operation has a much wider blast radius than a single-user action ([user token API](https://developer.atlassian.com/cloud/admin/user-management/rest/api-group-api-tokens/), [API-access revocation](https://developer.atlassian.com/cloud/admin/api-access/rest/api-group-api-token/), [account lifecycle](https://developer.atlassian.com/cloud/admin/user-management/rest/api-group-lifecycle/)).
- **Product allowlists do not protect every administrative path:** Organisation administration, organisation APIs, user-management and provisioning APIs are outside product IP allowlists; app/OAuth paths have further documented exceptions ([allowlist scope](https://support.atlassian.com/atlassian-cloud/kb/what-is-the-scope-of-ip-allowlists-in-atlassian-cloud/), [product allowlists](https://support.atlassian.com/security-and-access-policies/docs/specify-ip-addresses-for-product-access/)).
- **Export blocking is not a complete egress perimeter:** Atlassian documents API/app and browser limitations, and app-access rules do not revoke data already stored externally. Restrict or exclude a use when its mandatory boundary cannot be demonstrated ([export limits](https://support.atlassian.com/security-and-access-policies/docs/prevent-data-export/), [app-access coverage](https://support.atlassian.com/security-and-access-policies/docs/app-access-rule-coverage-summary/)).
- **Ownership metadata can create privilege:** A Confluence space owner receives all space permissions, and those permissions persist after ownership changes. Keep accountable business ownership distinct from native administrative ownership; explicitly remove obsolete effective grants ([space ownership](https://support.atlassian.com/confluence-cloud/docs/create-a-space/)).
- **No Rovo rollout is not proof of no Rovo access:** Atlassian says Rovo is automatically enabled on supported plans and documents both older blocklists and newer app/group access models. Verify actual denied access across the relevant Jira-family apps; public configuration API coverage was not established here ([AI availability](https://support.atlassian.com/organization-administration/docs/what-is-atlassian-intelligence/), [Enterprise access controls](https://support.atlassian.com/organization-administration/docs/manage-rovo-access-for-enterprise/)).

| **P-21 · Vulnerability deadlines** | **Firm automation / supplier assurance:** scanners, advisory evaluation and release gates cover owned automation; supplier-operated SaaS patching remains a provider assurance dependency, not a customer API action ([supplier security practices](https://www.atlassian.com/trust/security/security-practices)). |
| **P-22 · Synthetic non-production** | **Firm automation + restriction:** use isolated fixtures/bindings and reject copy activation. ## Recommended validation sequence

**Start with one narrow governed-asset path, not a generic SaaS controller.** Reuse supported rule/configuration interfaces; keep differentiated work in the requirements, declared patterns, policy and tests.

| Stage | Test scope | Required evidence |
| :--- | :--- | :--- |
| **Capability check** | Confirm tenant plans, rollout state, credential scopes and exact read/write endpoints; distinguish documented, callable and successful behaviour. | Per-property capability record: entitlement, API/version, authentication, read/write/test support, permissions, limitations and expiry/review date. No policy-operation pass based on documentation alone. |
| **Governed admission** | Use supplied synthetic application/owner/classification/approval fixtures to create one restricted Jira project and one private Confluence space. Apply classification and register evidence. | Invalid authority produces no normal release; permitted access works; unrelated access fails; ordinary users cannot bypass the governed creation path. |
| **Repeatable configuration** | Reapply the same declaration; introduce approved drift; change a shared pattern; interrupt a multi-step operation. | Stable identity mapping, no unnecessary change, affected-asset detection, timely observation, bounded correction and verified recovery. |
| **Timed access** | Activate/expire one-hour privilege and 30-day external access; withdraw urgent/routine access early. Exercise direct/inherited, managed/external and session/token paths. | Origin/deadline/effective-denial timestamps and explicit unsupported cases; no reliance on a successful delete response alone. |
| **Perimeter and restricted features** | Test approved/unapproved browser, API, app and controlled receiver paths using synthetic data. Verify public/anonymous access and excluded AI/copy features remain unavailable. | Evidence at the actual enforcement point; no claim of prevention when the receiver already obtained the payload. |
| **Signals and evidence** | Generate required events; check exclusions, correlation, source delay, collection outage, redaction and independent oversight retrieval. | Five-minute failure detection, immediate known-failure notification, preserved checkpoints, protected outputs and separated retention-category tests. |
| **Recovery** | Where entitled, back up and restore only the isolated synthetic dataset into an eligible clean target; reconcile excluded configuration and permissions. | Measured RTO/RPO and usable-service checks, including app access/public-link posture. Plan-blocked tests remain untested, not passed. |
| **Release decision** | Review each requirement's tested boundary, gaps and inherited dependencies. | Conformant within tested scope, approved exception, nonconformant or unknown; distinguish synthetic proof from production acceptance. |

## Recommendation

- **Proceed with API-backed asset and rule management:** the documented project, space, permission, classification and Automation interfaces justify a concrete lab implementation rather than further generic runtime design ([product APIs](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-projects/), [space APIs](https://developer.atlassian.com/cloud/confluence/rest/v2/api-group-space/), [rule API](https://developer.atlassian.com/cloud/automation/rest/api-group-rule-management/)).
- **Treat shared-policy CRUD as the first vendor blocker:** do not promise complete policy/configuration reconciliation while the public Control documentation says core operations are disabled ([Control policy status](https://developer.atlassian.com/cloud/admin/control/rest/api-group-policies/)).
- **Keep the firm's execution and evidence services explicit:** approvals, authoritative-input validation, timed expiry, drift scheduling, protected evidence and acceptance tests remain designed responsibilities, not features implied by SaaS CRUD.
- **Do not weaken the register to fit available APIs:** preserve the provisional targets and show unsupported control paths as gaps requiring restriction, additional capability or authorised treatment.

Publication of this assessment does not change the register's requirements, the main platform strategy or tenant configuration. It selects no runtime and records no controls as implemented.
